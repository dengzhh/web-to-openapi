# 写操作契约

> 适用：**所有对浏览器产生副作用的动作** —— 点击、输入、提交、上传、拖拽、快捷键。
> 读操作（抓取、查询、截图）不受本契约约束。
>
> 状态：**已实现**（`POST /api/v1/act/observe|find|click|type|scroll|drag|select|run`，实现见 `host/lib/action.js`）
> 建立日期：2026-11-14 ｜ 实现日期：2026-11-14

---

## 为什么现在先钉契约

填表单是浏览器自动化里最容易扩散的场景：每个表单都要重新处理目标定位、受控组件赋值、成败判定三件事。如果每个站点各写一遍，底层要改任何行为都得改 N 处。

但**现在还不知道真实表单长什么样**，所以只钉契约层，不钉实现层。

- 钉契约：返回什么、失败怎么表达、目标怎么定位 —— 这些不随表单形状改变
- 不钉实现：guard 阈值、settle 时长、press/release 拆分 —— 这些参数现在定就是猜

判据：**每次新增功能，问一句「有没有产生第二个直接调用 `callTool` 的点」。这个数字 > 3 就该收口。**

## 契约一：写操作必须返回统一回执

即使当前只有三个字段，字段名也定死。**只能加字段，不能改名、不能删。**

```json
{
  "dispatched": true,
  "effect": { "verdict": "changed", "signals": [] },
  "stale": null
}
```

| 字段 | 取值 | 语义 |
|---|---|---|
| `dispatched` | `true` / `false` / `"unknown"` | 输入是否真的发出去了。**超时必须是 `"unknown"`，不是 `false`** |
| `effect.verdict` | `changed` / `unattributable` / `none` | 页面是否真的变了。弱证据只能判 `unattributable`，不许冒领 `changed` |
| `effect.signals` | 数组 | 具体证据：`url:...` / `value-changed` / `mutations:N` / `focus:moved` / `tab:new` / `alert` |
| `stale` | `null` 或原因码 | `DOCUMENT_CHANGED` / `FRAME_DETACHED` / `REF_NOT_PRESENTED` / `NOT_VISIBLE` / `OBSCURED` / `DISABLED` |

已落实的扩展字段（调用方可以开始用）：

| 字段 | 取值 | 语义 |
|---|---|---|
| `input_kind` | `trusted` / `synthetic` | 输入通道。`trusted` = CDP `Input.*` 受信事件；扩展没回 `trusted` 时降级标 `synthetic`，**绝不假装** |
| `reached_target` | `true` / `false` / `null` | 是否确认输入到达目标。`null` = 无法证明（跨 frame 卫兵尚未实现），不填 `true` |
| `withheld` | `true` / 缺失 | press 之后目标元素已变，release 被送到视口外扣发，本次点击未激活任何元素 |
| `swapped` | `{before, after}` | 扣发时的元素指纹变化，用于定位“页面在按下瞬间做了什么” |
| `postcondition` | `{met, checks[]}` | 逐条断言的 met/unmet，如 `{expect:"url", value:"/search", ok:true}` |
| `retryable` | `true` / `false` | 该不该重试。`dispatched:"unknown"` 时恒为 `false` |

**为什么这条最重要**：表单填错比填不进去危险得多（金额填成数量，提交就是事故）。没有回执，调用方只能靠“看着像成了”。

## 契约二：写操作永不自动重试

`dispatched: "unknown"` 的处置是**上报给人**，不是重发。

理由：一次点击的超时可能意味着“已经提交了但响应没回来”。重试 = 双击提交，可能下两个订单、发两条消息。

- 禁止在工具内部、站点模块内部、调用方重试逻辑里对写操作做透明重试
- 需要重试时，先 `observe` 一次确认副作用是否已经发生，再决定
- 读操作可以随便重试——读没有副作用，这是两者的根本区别

---

## 契约三：目标一律用 ref，业务代码禁止写 CSS 选择器

- 定位链路：`observe` → `find`（按 label/placeholder/name/id 等语义筛选）→ `ref` 派发；只有 ref 才进派发门禁
- `find` 是「语义 → ref」的桥接：只查 observe 登记过的集合，不越过 known-set 直接定位新元素
- 站点模块里**不允许**出现 `document.querySelector('.btn-submit')` 这类硬编码选择器
- 用 `observe` 没返回过的 ref，必须报 `REF_NOT_PRESENTED` —— 这条挡住“凭记忆编元素”

理由：选择器随站点改版即废，而且会静默命中错元素（`querySelector` 永远返回第一个匹配，不会告诉你“这里其实有三个按钮”）。ref 至少能被“本轮是否呈现过”这道门禁检查。

## 契约四：赋值方式由调用方声明，底层不许替它选

| 方式 | 适用 | 行为 |
|---|---|---|
| `set-value` | 原生 input / textarea | 程序化赋值 + 手动派发 `input` + `change` 事件 |
| `keyboard` | 受控组件（React/Vue）、contenteditable、需要触发校验的场景 | CDP `Input.dispatchKeyEvent` 真键盘输入 |

**必须由调用方显式指定**，因为两者对受控组件的结果完全不同：

- React 受控组件：直接 `el.value = x` 不触发 `onChange`，业务逻辑不认这个值，提交时是空的
- 而真键盘输入慢、且会被输入法/快捷键干扰，简单表单没必要用

底层如果“聪明地”自动选择，调用方就永远不知道刚才那次为什么失败。

## 新增工具检查清单

加任何带副作用的工具前，逐条过一遍：

- [ ] 返回结构是否符合契约一（三个字段名不改）
- [ ] 超时是否返回 `"unknown"` 而不是抛错或 `false`
- [ ] 是否**没有**任何自动重试路径（含 `for` 循环里的重试、上层的 retry 包装）
- [ ] 目标是否走 ref，有没有硬编码选择器
- [ ] 赋值/点击方式是否由参数显式声明
- [ ] 写操作端点是否会被鉴权 / 公开路径规则拦截（不应匿名可达）

## 将来填表单时会遇到的已知坑（记录用，不必现在解决）

1. **受控组件**：见契约四。这是最容易踩且最难自查的——页面看起来填上了，提交是空的
2. **iframe 里的表单**：ref 是 per-frame 的，跨 frame 不能复用
3. **组件库的复合控件**：日期选择器要“点开日历再点某天”，不是一次赋值能完成——用 `select`（下拉/自定义下拉）+ `run`（多步编排）组合解决
4. **校验时机**：有的表单失焦才校验，有的输入即校验，`blur` 要显式触发
5. **文件上传**：`chrome_upload_file` 走的是 CDP `DOM.setFileInputFiles`，和普通赋值不是一条路
